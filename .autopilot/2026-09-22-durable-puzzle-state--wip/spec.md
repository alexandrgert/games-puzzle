# Спецификация: устойчивое сохранение партии и выпуск APK

## Задача

Игрок не должен терять разложенную доску, ходы и время, если переключился на другое приложение, Android пересоздал экран или выгрузил процесс. Исправление должно быть подтверждено тестами и debug APK, а будущий выпуск — подготовленным черновиком release notes.

## Решение

Текущая партия сохраняется в версионированном JSON локально после каждого игрового изменения и перед уходом экрана в фон. При возвращении восстанавливается та же доска. Таймер в фоне не идёт. Повреждённое или несовместимое сохранение не ломает запуск: оно удаляется и начинается новая партия.

## Решения по реализации

- Канонический снимок партии — JSON с `schemaVersion`; массивы и игровые поля валидируются доменом при чтении. Это переносимый и мигрируемый контракт вместо Android-специфичного объекта в `Bundle`.
- `SavedStateHandle` остаётся быстрым слоем для обычного пересоздания экрана, но постоянное локальное хранилище является резервным источником после уничтожения процесса.
- Хранилище скрыто за интерфейсом, чтобы JVM-тесты использовали in-memory реализацию, а Android — DataStore Preferences. Ключ включает puzzle ID, размер и режим статистики.
- Сохранение сериализуется и выполняется асинхронно; lifecycle-команда паузы обновляет снимок до фонового периода. Последующие записи не должны перетирать более новое состояние старым.
- Завершённая партия хранит зафиксированное итоговое время. Явный отказ от партии очищает активный снимок; обычная навигация/фон его не очищают.
- Тест каталога читает фактически поставляемые assets, а не дублированный список.
- CI всегда строит debug APK; подписанный release остаётся условным и использует только существующие секреты.
- Версия приложения в этой работе не повышается: release notes создаются как `draft` для следующего релиза, чтобы не выдавать незапущенную публикацию за состоявшийся релиз.
- D01 (таск 02): локальная sandbox-среда разрывает Gradle daemon networking, а прямой запуск JVM завершается на Kotlin-компиляции без результата. Позднее пользователь уточнил: APK собирается только на GitHub, поэтому локальная APK-сборка больше не является критерием приёмки.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `PlaySession` | доска, ходы, таймер, снимок | `snapshot`, `restore`, `pauseTimer`, `resumeTimer` | расчёт накопленного времени и проверку снимка |
| `ActivePlaySessionStore` | постоянные снимки активных партий | `load`, `save`, `clear` по ключу партии | JSON, schema version и DataStore Preferences |
| `PlayViewModel` | координация сессии, UI-состояния и сохранения | `start`, игровые команды, `onBackground`, `onForeground`, `abandon` | выбор источника восстановления и порядок записей |
| `PlayScreen` | Android lifecycle экрана | события жизненного цикла в ViewModel | Compose-наблюдатель lifecycle |

Основные тестовые швы: публичный контракт `PlaySession` и интерфейс `ActivePlaySessionStore`, внедряемый в `PlayViewModel`.

## Вне рамок

- Синхронизация партии между устройствами: R01 требует локального продолжения; серверный sync является отдельной функцией.
- Публикация GitHub Release: R07 требует черновик, а публикация — внешнее необратимое действие.
- Локальная APK-сборка: G01 явно требует собирать APK только на GitHub.
